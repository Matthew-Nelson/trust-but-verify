# Harness review, round 4: fault-injection tests, `harness-v1.1` → `0ece60f` against `spec-v1.5`

Reviewer: the same blind reviewer as rounds 1 to 3. Static review only; I saw no implementation, no broken variant and no run against either. Read: `spec-v1.4-to-v1.5.diff`, `spec/SPEC.md` (v1.5), `spec/PROPOSALS.md` (HP-27..30), `spec/reviews/08-disposition.md`, the complete `harness-v1.1-to-0ece60f.diff` (9 files), and the current `lib/pgproxy.ts` and `tests/api/faults.graybox.test.ts` in full; plus a check that the proposal gate left nothing behind in `lib/`, `tests/` or the runner configs.

**Summary.** The spec-v1.5 "Fault injection" bullet is sound and the HP-29 latency definition is measurable, fair, and faithfully implemented. The proxy's framing and idle test are correct against the PostgreSQL v3 protocol for simple, extended, pipelined and partly-received traffic; an injected statement can never land inside a message or a request cycle, its replies can never reach the api, and anything the proxy cannot frame or apply ends in an inconclusive skip rather than a pass. Neither test can fail a conforming api on the merits; both catch the three red-team behaviours as described (non-canonical 500, changed redirect, multi-second delay). The fault is confined to the spawned instance's own sessions. Nothing outside the new files moved except two additive helpers and docs. Six nits, none blocking.

## 1. The spec-v1.5 text

**Fault injection bullet (HP-28).** Unambiguous about placement (one spawned instance, proxy in front of the verification database), about the two permitted deviations from "relay unchanged", and about when injection may happen ("idle between transactions: last ReadyForQuery `I`, no request outstanding or partly sent"). It states who is responsible for what: the database must accept plaintext from the harness host; the api must accept plaintext when its URL does not demand encryption; an api that undoes the fault makes the test inconclusive, never passed. Consistent with "Shared database" (nothing shared is touched), with R-HEALTH-2's "unspecified while unreachable" (this fault is not unreachability), and with the Configuration exceptions list, which now names these tests. One wording tension (HR4-01): the bullet says a request the api cannot complete because of a rejected statement "is an internal error (R-ERR-7)", while HP-30, which would have required a 500 for exactly that, was declined. The harness reads it the lenient way (no 500 → inconclusive), so no conforming api is harmed, but the sentence could be read as the declined rule. The implementation-facing sentence ("must accept an unencrypted connection when its `DATABASE_URL` does not require encryption") is the default of libpq (`sslmode=prefer`), sqlx and tokio-postgres; it binds the implementation only in the way the disposition says, and the Configuration default URL carries no `sslmode`, so it does not contradict anything.

**HP-29 latency definition.** Measurable: B is the slowest of 20 same-instance, same-link, same-client requests, 10 of them interleaved with the faulted GETs so they see the same load; the bound max(4B, B + 1 s) is recorded with B as an annotation. Fair: a synchronous recorder spends one failed statement (sub-millisecond to a few ms) and an asynchronous one spends nothing, both far inside B + 1 s. A seconds-long delay cannot pass while B < ~1 s, which it is on any machine where the rest of the suite is meaningful; a sub-second single retry (say 900 ms backoff) would pass, which is the bound SPEC chose and is stated plainly. On a loaded machine, a sustained slowdown raises B through the HEADs and so raises the bound; only a one-off stall of more than one second that hits one faulted GET and none of the 20 reference requests could fail a conforming api, and the measurement is taken in the harness process (`res.ms`), so a Node event-loop pause would count against the api (HR4-03). I rate that a rare flake, not a design fault.

**"canonical form" and status line.** Unchanged from v1.4 apart from the Status line, which correctly says v1.5 adds no api-behaviour rule and that HP-30 was declined.

## 2. The proxy against the wire protocol (`lib/pgproxy.ts`)

I walked the state machine against the v3 message catalogue.

- **Startup.** First packet is framed by its own length (`len`, code). SSLRequest (80877103) and GSSENCRequest (80877104) are answered `N` by the proxy and never forwarded; the client then continues in plaintext (`prefer` semantics). A client that insists on TLS closes, and the test fails at setup with the SPEC reference (see HR4-02 for when that is the operator's URL, not the api). CancelRequest is forwarded and the connection marked `cancel` (nothing else ever travels on it). A protocol-3 StartupMessage flips to `typed` with `pendingSyncs = 1`, so nothing can be injected until the first ReadyForQuery. A direct-TLS first byte (0x16) or an unparseable first packet makes the session `opaque` (pure passthrough, counted), which `settled()` turns into an inconclusive skip.
- **Typed framing.** Both directions reassemble whole messages (`1 + len`) before acting, so a message split across TCP writes is never forwarded partially and an injected Query can never be interleaved inside one. Authentication (`p`, `R`), ParameterStatus, BackendKeyData are forwarded unchanged.
- **Idle test.** Injection requires: `typed` phase, startup complete, no swallow in progress, `pendingSyncs == 0`, no open extended-protocol batch, `txStatus == 'I'`, and `cbuf` empty. `pendingSyncs` is incremented on exactly the client messages that produce a ReadyForQuery (`Q`, `S`, `F`) and decremented on each `Z`, so pipelined simple queries and multiple Syncs are counted correctly; `P/B/D/E/C/H` open a batch that only `S` closes, so nothing is injected mid-batch or after a lone Flush; COPY mode stays under its enclosing `Q`/`S` until its `Z`; a session parked inside a transaction (`Z:T`/`Z:E`) is never touched. The `cbuf` check implements "partly sent" exactly as v1.5 words it. The two call sites (`onClient` after forwarding when the buffer is drained; `onBackend` after forwarding a `Z`) are the only moments a session can become idle.
- **Ordering and isolation of the injected query.** The injected `Q` is written to the upstream socket synchronously right after the `Z` is forwarded, so any message the api sends in reaction to that `Z` is queued behind it on the same socket. The backend therefore answers the injected query first (one `Z` even for the two-statement string; `E`+`Z` on error), and the proxy swallows everything up to and including that `Z` before forwarding the api's own responses. The only backend messages that could arrive during the swallow window belong to the injected query (CommandComplete, ErrorResponse, NoticeResponse); neither `SET` touches a reported GUC, so no ParameterStatus is generated, and even one would be harmlessly swallowed. No reply to an injected query can reach the api, and no api reply can be swallowed, because the swallow window ends at the first `Z` and the api's next request cannot have been answered before it.
- **Future sessions.** A session completing startup after `apply()` is injected at its first `Z`, before the client's first query is forwarded (the client waits for `Z` before sending). Multiple generations (R-ERR-7 applies READ ONLY, then READ ONLY + empty `search_path`) are tracked per session with `applied < generation`.
- **Restore detection.** `Q` text and the SQL of `P` are scanned once a fault is pending or applied; `READ WRITE`, `(default_)transaction_read_only`, `RESET/DISCARD ALL` and `search_path` are flagged with the generation, so a connect-time `SET search_path = public` sent after a read-only-only fault is correctly ignored by the R-REDIR-6 test and by R-ERR-7's phase-1 reasoning, and correctly makes phase 2 inconclusive. (`SHOW search_path` would also be flagged; see HR4-05.)
- **Failure paths.** A rejected injected statement sets `injectFailed`, a never-idle session shows as `lagging`, an opaque session as `opaque`; `settled(5000)` is `ok` only if all are zero, and `applyFault` turns anything else into an inconclusive skip with the counts and errors in the note. `close()` destroys every session and closes the listener; `afterEach` pops cleanups LIFO (api first, then proxy) and runs on failure, timeout and skip. Nothing in the shared database is altered: the two `SET`s are session-local and the instance's own successful writes before the fault are ordinary links and clicks.

I found no path by which the injection corrupts a session or lets a hidden reply through.

## 3. The two tests against SPEC

**R-REDIR-6.** Baseline: a warm-up GET and HEAD (excluded from B), 10 GETs that must be 302 to `link.url`, and 11 click rows must be stored within 2.5 s (R-REDIR-4). The reference response is `baseline[0]`; Content-Type and body are dropped from the comparison if they already vary across the baseline, exactly as R-REDIR-6 allows; a varying Cache-Control is inconclusive (SPEC gives no escape for it, so this is lenient, never a false failure). Fault: READ ONLY applied and settled on every session. Then 10 HEAD/GET pairs; 2.5 s later the stored count must still be 11. Inconclusive, in order: any read-write restore; any click still stored; HEAD broken too. Then the two assertions SPEC states: every faulted GET equals the reference on the compared fields, and every faulted GET's headers arrived within max(4B, B + 1 s).

  *False failure?* A conforming api's lookup is a SELECT, which works under READ ONLY; its INSERT fails immediately (`25006`) and, whether recorded synchronously or asynchronously, the 302 is unaffected and arrives within milliseconds; a pool that drops the errored connection reconnects in milliseconds and the new session is injected at startup. I see no path to a failure other than the rare stall in HR4-03. An api that couples lookup and insert in one statement or transaction and answers non-302 when the insert fails *is* a R-REDIR-6 violation, so failing it is correct.

  *False pass?* A changed status/Location/Cache-Control fails the equality; a body or Content-Type that only changes under the fault fails too; a retry/backoff of seconds fails the bound; an api that silently restores read-write cannot pass (inconclusive); an api whose clicks still land cannot pass. Good.

**R-ERR-7.** Phase 1 (READ ONLY): two creates and a delete; `writesHeld` is checked directly in the database. Phase 2 (READ ONLY + empty `search_path`): list, get, stats, redirect, create, delete, all with a 10 s client timeout recorded rather than thrown. Every 500 received, on any path including `/{code}`, must parse to exactly the canonical object; `lib/http.ts` additionally throws on any non-canonical 500 under `/api/...`, and `timed()` rethrows that. Inconclusive if the api undid the fault (flagged SQL, or a write that succeeded) or if no request got a 500.

  *False failure?* Only a 500 with a non-canonical body fails, which is the rule. An api that answers 503 everywhere is inconclusive, as HP-30's decline requires. The 500-body check runs before the inconclusive checks, which is right: a non-canonical 500 is a violation whether or not the fault held.

  *False pass?* A non-canonical 500 anywhere is caught; a canonical 500 under `/api/` with a non-JSON Content-Type is caught by R-ERR-1; no-500 cannot pass. Good.

**Reporting.** Every inconclusive branch goes through `inconclusive()`, which annotates and then `ctx.skip(note)`s with the `inconclusive (gray-box):` prefix the report generator already recognises; nothing in either test can end in "passed" without the fault having demonstrably taken effect. The `API_BIN`/`DATABASE_URL` skips use the existing prefixes. **Confinement:** the instance has its own port and `PUBLIC_BASE_URL`, only this file talks to it, the faults are session-local, and `storedClicks`/`linkExists` use the harness's own unproxied pool.

## Findings

### HR4-01 — nit — SPEC "Fault injection" bullet — "is an internal error (R-ERR-7)" versus the declined HP-30

The sentence "a request the api cannot complete because the database rejected a statement is an internal error (R-ERR-7)" reads as if such a request *must* get R-ERR-7's 500, which is the rule HP-30 proposed and Matthew declined. The harness applies the lenient reading (no 500 → inconclusive), so no conforming api is affected; the risk is only that an implementer or a future harness author takes the sentence as a requirement. **Fix:** at the next revision, "… and, when the api answers such a request with a 500, R-ERR-7 applies to it".

### HR4-02 — nit — `tests/api/faults.graybox.test.ts:45-66` — an operator `DATABASE_URL` that demands TLS fails the test instead of skipping it

`viaPort` keeps the verification URL's parameters, so `sslmode=require|verify-ca|verify-full` (or PG17 `sslnegotiation=direct`) in the operator's `DATABASE_URL` makes a conforming api refuse the proxy's `N` and the test *fails* at setup ("did not become healthy …"), or, in the direct-TLS case, reach health through an opaque session and fail `readySessions > 0`. SPEC puts the plaintext obligation on the verification run, so this is operator misconfiguration, and the failure message says so, but it is still a conforming api reported as failing. **Fix:** before spawning, if the URL's `sslmode` is one of the three requiring values or `sslnegotiation=direct`, skip as `inconclusive (gray-box): DATABASE_URL requires encryption; the fault proxy cannot frame an encrypted session`; and in `faultableInstance`, when `readySessions === 0 && opaqueSessions > 0`, report inconclusive rather than failing.

### HR4-03 — nit — `tests/api/faults.graybox.test.ts:197-202` — one-off stalls count against the api

B + 1 s is generous, but a single stall of more than one second that hits one faulted GET and none of the 20 reference requests fails a conforming api, and the latency is measured in the harness process, so a Node GC/event-loop pause of that size would too. Rare on a machine where the rest of the suite is usable. **Fix (optional, harness policy, SPEC is silent):** if the only failed assertion is the latency bound, repeat the fault phase once (new 10 HEAD/GET pairs, same B rule) and fail only if it exceeds the bound twice; annotate both runs.

### HR4-04 — nit — `README.md` fault-injection bullet versus `COVERAGE.md`

README says a test skips as inconclusive "in four cases" and omits two of R-REDIR-6's five (HEAD also broke; Cache-Control varies between normal redirects), which COVERAGE and the code have. **Fix:** list all five for R-REDIR-6 and the three for R-ERR-7, or drop the count.

### HR4-05 — nit — `lib/pgproxy.ts:31-34` — restore patterns are broader than "restores"

`\bsearch_path\b` and `\b(default_)?transaction_read_only\b` also match `SHOW search_path`, `SELECT current_setting('transaction_read_only')` and comments, so an api that merely *reads* these settings after the fault would be reported inconclusive. That is the safe direction (never a pass, never a failure), so it is a nit. **Fix:** require a `SET`/`RESET`/`DISCARD`/`BEGIN … READ WRITE`/`SET TRANSACTION` form, e.g. `^\s*(set|reset|discard|begin|start)\b` combined with the current terms.

### HR4-06 — nit — `SELF_CHECK.md` run 12 — the changed idle condition and the full fault path are unexercised

SELF_CHECK says so itself. The proxy was last driven by the scratch script before the "partly sent" condition was added, and no run has yet reached the fault phases. Nothing in my reading suggests a defect, but this is the one component in the harness whose correctness rests on protocol reasoning rather than on a run. **Fix:** see "What to run".
