# Role: verifier (coordinator session)

Runs in the main repo after `mutants-v1`. Produces the evidence and the report.

1. **Reveal the holdout.** First re-compute both seals in `provenance/HOLDOUT_SEAL.md` from their bundles and record the hashes. Seal 2 is the one in force, and seal 1 is published alongside it so the run-5 changes can be diffed. Then copy the seal-2 holdout into `harness/holdout/` and commit it after `impl-v1`, with a message stating its source and that it was hidden until now. Also publish both bundles' unredacted `SELF_CHECK.md` and holdout results.
2. **Audit isolation.** Search the implementer agents' transcripts for any access to the holdout location, and the red team's for any access to `harness/`. Record the method and the result.
3. **Build `tools/`.**
   - `mutate`: for each patch in `mutants/`, create a temporary worktree at `impl-v1`, apply the patch, build, and start the service on a free port against a fresh database. Run public + holdout + invariants (+ UI for web mutants), record **killed / survived**, and record whether the killing test carries the mutant's requirement ID ("targeted kill") or a different one ("incidental kill").
   - `trace`: parse every `R-*` ID from `spec/SPEC.md`, join it with the test results (Vitest/Playwright JSON reporters) and `harness/COVERAGE.md`, and mark each ID **verified**, **gray-box verified**, **mutant-verified only**, **failing**, **pending** or **unverified**. A skipped gray-box test is **pending**, never a pass. Use the skip note prefix (`pending (gray-box): API_BIN is unset` vs `gray-box: DATABASE_URL is unset`) to say which variable was missing (HP-20). The final run must set both, so nothing is pending. Vitest's JSON reporter drops skip notes and annotations (checked on 4.1.11; see `spec/reviews/05-disposition.md`, HR2-05), so collect results with a custom Vitest reporter that records each test's skip note and annotations. Fail the report build if a gray-box skip has no recognized prefix (`pending (gray-box):`, `gray-box: DATABASE_URL is unset`, `inconclusive (gray-box):`). An `inconclusive` R-PRIV-1 skip is reported as pending. For R-PRIV-1, use a `DATABASE_URL` host whose resolved address differs from the client address, and check any log-search failure for a logged database address before reporting it (HR2-03). List that residual path under "what this does not prove".
   - `report`: write `reports/VERIFICATION.md` and an HTML version with the results table from the README, the traceability matrix, the mutant table, fuzzing stats, public-vs-holdout pass rates, the cargo-mutants score (labeled as implementer-test quality), audit results, the isolation audit, and the "what this does not prove" section from METHOD.md.
4. **Run everything** and save the raw outputs under `reports/raw/`.
5. **Gap loop.** For each surviving mutant, describe the missed behavior **in spec terms only** (requirement ID + the observable behavior that went undetected, without the patch) and hand that to a fresh harness-author agent working in a spec-only workspace. Re-run. Log every round in `provenance/LOG.md`. Any real implementation bug found along the way goes to a fresh implementer agent, and the fix is re-verified.
6. **Make it reproducible.** Add `make verify`, which runs the whole pipeline from a clean clone. Add a GitHub Actions workflow with a Postgres service that runs it on every push, fails if `harness/` changes in the same commit as `impls/`, and publishes the HTML report to GitHub Pages.
7. **Write the human acceptance checklist.** Write `reports/HUMAN_ACCEPTANCE.md`: a 10–15 step script Matthew runs against the live app, with a place to record pass/fail and notes.
8. **Update the README** results table with real numbers and tag `verified-v1`.

**Proxy variables (HR3-02).** Before `pnpm fuzz`, the verify run fails if `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY` or their lowercase forms are set. Schemathesis honours them even for localhost, so they would route the fuzz run through a proxy. CI unsets them explicitly.

**Corrections recorded at phase start (2026-10-18, coordinator):** step 1 predates seals 3 and the runner's layout. All three seals were recomputed, and **seal 3** is the one in force. The holdout was revealed at the repo root as `holdout/`, not `harness/holdout/`, because its config resolves `../harness/lib` and `harness/scripts/run-holdout.mjs` expects `../holdout`. `mutate` reuses one worktree at a fixed path (`.work/mutant-wt`), reset to `impl-v1` before each mutant, instead of a new temporary worktree each time. That keeps the api binary at one path (Postgres.app asks per client path) and the builds incremental. Mutant-verified requirements (R-ERR-7, R-REDIR-6) get no coordinator-written fault-injection check, because the coordinator has seen the mutants. Their evidence comes from round 0 and the gap loop.
