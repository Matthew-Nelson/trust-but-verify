# Disposition of post-freeze proposals HP-23..25 and deferred nit HR2-02

**Source:** the first build against `harness-v1` (runs 8 and 9). Every item was confirmed by the coordinator: HP-23 by reading the test, and HP-24 and HP-25 by reproducing the fuzz run against a fresh database (`provenance/LOG.md`, "Coordinator verification of runs 8 and 9").
**Decision:** these fixes change a frozen harness after an implementation exists, which is the step most likely to shape the tests around the code. Matthew chose a blind fix with re-review (in session: "Blind fix + re-review"). So: the coordinator amends SPEC; the original harness author, who has never seen an implementation, makes the harness changes; and the blind harness reviewer checks the diff. The result is tagged `harness-v1.1`.

| ID | Raised by | Coordinator check | Resolution | Who |
|---|---|---|---|---|
| HP-23 | web implementer | **Confirmed.** The R-UI-1 test asserts `required === false` on every entry in `form.elements`. `HTMLButtonElement` has no `required` property, so a `<button>Shorten</button>` reads `undefined` and fails, although SPEC allows it. The holdout's R-UI-1 check reads only the two textboxes and is unaffected. | No SPEC change. Harness: a control fails only if `required` is `true` (or only `input`, `select` and `textarea` are checked). | harness |
| HP-24 | api implementer | **Confirmed. A contradiction inside SPEC.** "Verification rules / Fuzzing" ran every check except `positive_data_acceptance`. Schemathesis's `negative_data_rejection` treats an undefined query parameter as invalid data and expects a 4xx, but R-ERR-3 and "Query integer" require it to be ignored. Every conforming api fails 2 cases. | **SPEC v1.4:** generation never adds parameters the schema doesn't define. `negative_data_rejection` stays on for every other kind of invalid input. Harness: Schemathesis 4.29.1 provides `[generation] allow-extra-parameters = false`. | coordinator + harness |
| HP-25 | api implementer | **Confirmed.** `--max-redirects 0` makes Schemathesis (through `requests`) raise "Exceeded 0 redirects" on every 302 from `/{code}`, so no conforming api can pass. SPEC said only "does not follow redirects". | **SPEC v1.4:** a 3xx is recorded and checked as the operation's response, never followed and never counted as an error. Harness: send requests without following redirects (for example a `before_call` hook that sets `allow_redirects=False`; `fuzz.mjs` currently blanks `SCHEMATHESIS_HOOKS`). External hosts must stay unreachable from the fuzz run. | coordinator + harness |
| HR2-02 | harness reviewer (round 2) | Deferred from `05-disposition.md`. | **SPEC v1.4:** R-PRIV-1's "canonical form" is defined as the client address exactly as the api's socket observes it, with an IPv4-mapped IPv6 address taken in its plain IPv4 form. This matches the harness's `canonicalForms`. No harness change. | coordinator |
| HR2-01 | harness reviewer (round 2) | Deferred from `05-disposition.md`. | **SPEC v1.4:** the Status line no longer calls v1.2 "no behavior change" and names the R-ROUTE-2 `%2F` decision. | coordinator |
| HR2-04 | harness reviewer (round 2) | Deferred to the next harness change. | Harness: fix the stale `spec-v1.2` strings (README, package.json, COVERAGE note) and point them at `spec-v1.4`. | harness |

**What doesn't change:** no rule about api behavior. Both builds already behave as v1.4 says, because v1.4 resolves the fuzzing rule toward R-ERR-3 and R-REDIR-1, which were already there and already tested. The holdout is untouched, so seal 3 stays in force.

**The risk being managed:** HP-24 and HP-25 were found by running a real implementation, and the harness change is being made with that knowledge. The guard is that each fix follows from SPEC text alone (R-ERR-3; R-REDIR-1 plus "does not follow redirects"), not from the implementation's behavior. The harness author gets SPEC and these resolutions, not the implementation, its output or its fuzz report. The reviewer checks that each change is the narrowest one that resolves the contradiction, and that no check gets weaker for any other input.
